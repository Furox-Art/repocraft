# repocraft

Deterministic Python project scaffolding from a validated spec.

`repocraft` turns a small YAML spec into a complete Python project: packaging
metadata, a `src/` layout, tests, lint and type-check configuration, CI, CodeQL,
Dependabot, and a JUnit gate that rejects skipped tests. The same spec and the
same `repocraft` version always produce byte-identical output.

Natural-language input and GitHub repository creation are roadmap items. The
core in this release is the deterministic part: spec in, files out.

## Status

Version 0.1.0 is the phase-1 core:

- strict JSON Schema validation with readable errors;
- duplicate-key rejection in YAML;
- library and CLI project templates;
- MIT and Apache-2.0 license generation;
- golden snapshot tests that compare every generated byte;
- smoke tests that install each generated project and run its own ruff, mypy,
  pytest coverage gate, and JUnit skip gate.

The interactive wizard, free-form NL-to-spec front end, GitHub repo creation and
push, and the MCP server are not implemented yet.

## Requirements

- Python 3.10 or newer.

## Installation

The package is not published on PyPI, and the GitHub repository has not been
created yet. From this checkout:

```bash
python -m pip install .
```

## Usage

Write a spec:

```yaml
schema_version: 1
project:
  name: example-cli
  package: example_cli
  description: An example command-line application.
  type: cli
  license: Apache-2.0
  author: Your Name
  version: 0.1.0
  python: ">=3.10"
  cli:
    command: example-cli
  repository:
    owner: your-user
    name: example-cli
    private: true
```

Validate it:

```bash
repocraft validate spec.yaml
```

Plan the output without writing anything:

```bash
repocraft render spec.yaml example-cli --dry-run
```

Render it:

```bash
repocraft render spec.yaml example-cli
```

`render` refuses an output directory that already contains files. It never
overwrites or merges into existing work.

### Spec fields

| Field | Required | Meaning |
|---|---|---|
| `schema_version` | yes | Must be `1`. |
| `project.name` | yes | Distribution name, lowercase letters, digits, and hyphens. |
| `project.package` | yes | Import package name, lowercase letters, digits, and underscores. |
| `project.description` | yes | One-line description, 10 to 200 characters. |
| `project.type` | yes | `library` or `cli`. |
| `project.license` | yes | `MIT` or `Apache-2.0`. |
| `project.author` | yes | Copyright holder and package author. |
| `project.version` | no | Semantic version, default `0.1.0`. |
| `project.python` | no | `>=3.10` through `>=3.14`, default `>=3.10`. |
| `project.cli.command` | for `cli` | Console script name. Forbidden for `library`. |
| `project.repository` | no | `owner`, `name`, and `private` (default `true`). |

## Determinism contract

For a fixed spec and a fixed `repocraft` version:

- output paths and file contents are byte-identical;
- entries are rendered in sorted order;
- files use LF line endings and a trailing newline;
- no timestamps, random identifiers, or environment values are embedded;
- the generated MIT copyright line carries the author but no year.

The golden tests in `tests/golden/` enforce the contract file by file.

## Development

```bash
python -m venv .venv
. .venv/bin/activate  # Windows: .venv\Scripts\activate
python -m pip install -e ".[dev]"
python -m ruff check .
python -m mypy
python -m pytest --cov=repocraft --cov-branch --cov-fail-under=100
```

The smoke tests install the rendered fixtures into temporary target directories
with `--no-deps --no-build-isolation`, then run the generated projects' own
quality gates. Hatchling is a dev dependency for exactly that reason.

CI runs the suite on Python 3.10 through 3.14 and rejects skipped tests through
`scripts/check_junit.py`.

## Roadmap

1. Interactive wizard for people who do not want to write YAML.
2. Free-form natural language to spec through an OpenAI-compatible endpoint,
   with a confirmation step before any file is written.
3. GitHub repository creation and push, private by default.
4. MCP server exposing the same validated core.
